# Hub v2.34

**Hub**는 사내 문서·회의·연결 서비스·업무 기록을 한곳에 모으고,  
검색 → 근거 확인 → AI 정리 → 담당자 업무 → 관리자 검토까지 이어 주는 **사내 업무 AI 허브**입니다.

처음 온 구성원도 기존 자료와 근거를 빠르게 찾고, 해야 할 일을 놓치지 않도록 만드는 것이 핵심 목표입니다.


---

## 제품 소개

Hub는 단순히 AI에게 질문하는 챗봇이 아니라, **회사 안에 흩어진 자료를 실제 업무와 연결하는 사내 업무 플랫폼**을 목표로 합니다.

기본 흐름은 다음과 같습니다.

```text
자료 수집
 → 검색
 → 근거 확인
 → AI 정리
 → 회의/결정
 → 할 일 생성
 → 담당자 수행
 → 결과 제출
 → 관리자 검토
 → 기록 축적
```

이 구조를 통해 다음 문제를 줄이려 합니다.

- 필요한 자료가 어디 있는지 몰라 다시 찾는 시간
- 회의에서 결정된 내용이 실제 할 일로 이어지지 않는 문제
- AI가 답했지만 원문 근거를 확인하기 어려운 문제
- 담당자와 결정권자의 역할이 뒤섞이는 문제
- 업무 완료 이후 결과와 변경 이력이 남지 않는 문제
- 기존 GitHub·Drive·Slack·Notion 자료가 각각 분리되어 있는 문제

Hub는 기존 협업 도구를 모두 대체하기보다, **기존 도구에 흩어진 정보를 모아 검색·판단·업무 실행을 연결하는 허브**를 지향합니다.

### 사용자 관점

일반 사용자는 자신에게 필요한 자료와 근거를 빠르게 확인하고, 배정된 업무를 수행한 뒤 파일이나 URL로 결과를 제출합니다.

관리자는 AI가 만든 결과를 그대로 승인하지 않고, 원문·근거·제출 자료를 확인한 뒤 담당자 지정, 업무 확정, 승인·반려와 같은 최종 판단을 수행합니다.

즉 Hub는 **AI 자동화와 사람의 최종 판단을 분리**하는 구조를 기본으로 합니다.

### 기획·사업 관점

Hub가 지향하는 가치는 다음과 같습니다.

- 신규 구성원도 기존 기록과 근거를 빠르게 찾아 업무 맥락을 이해할 수 있도록 지원
- 검색 결과를 회의·TODO·담당자·승인 흐름까지 연결해 정보 탐색 이후의 실제 업무까지 지원
- 조직의 문서·회의·업무 결과를 지속적으로 축적해 재사용 가능한 데이터 자산으로 전환
- 기존 시스템을 버리지 않고 Connector를 통해 함께 사용할 수 있는 구조
- 프로젝트와 조직이 커져도 관리자·일반 사용자 역할과 기록을 분리해 운영 가능한 구조

## 개발 관점

Hub는 백엔드, 프론트엔드, Python AI 서비스가 서로 독립적으로 역할을 가지되 하나의 업무 흐름을 완성하도록 구성되어 있습니다.

### Backend — 운영·배포·유지보수 중심

Spring Boot 백엔드는 단순 API 제공 계층이 아니라 **업무 규칙과 운영 안정성을 보장하는 중심 계층**입니다.

주요 책임:

- ADMIN / MEMBER 인증·권한 분리
- 프로젝트·문서·회의·TODO 상태 관리
- 담당자 지정과 완료 제출·승인·반려 규칙
- 검색 결과와 Evidence 연결
- 가입 승인, 조직 관리, 검색 정책, 관리 이력
- Connector와 외부 서비스 수집 작업 관리
- 운영 DB migration과 서비스 상태 확인

운영에서는 개발 저장소와 실제 배포를 분리합니다.

```text
Hub main
 → CI 검증
 → Server 저장소
 → 중앙 배포
 → Docker 이미지 빌드
 → PostgreSQL / AI / Backend / Caddy 기동
 → Health Check
 → 실제 공개 주소 검증
```

이 구조는 코드가 main에 들어갔다는 사실과 실제 운영 서비스가 정상이라는 사실을 분리해 확인하기 위한 것입니다.

유지보수 관점에서는 다음 항목을 중요하게 봅니다.

- Flyway를 통한 DB 변경 이력 관리
- health endpoint를 통한 서비스 상태 확인
- 운영 Secret과 저장소 코드 분리
- CI 단계의 build/test/typecheck/migration 검증
- 장애 발생 시 Backend·AI·DB·Proxy 계층을 나누어 원인을 추적할 수 있는 구조
- 관리자 교체 이후에도 프로젝트 단위 기록과 제출물이 유지되는 구조

### Frontend — UI/UX와 화면 흐름 중심

React + TypeScript 프론트엔드는 기능을 단순히 화면에 나열하기보다, 사용자가 다음 행동을 자연스럽게 이해하도록 흐름을 구성합니다.

대표 사용자 흐름:

```text
자료 찾기
 → 검색 결과 확인
 → 근거/원문 열기
 → 관련 업무 확인
 → 담당 업무 수행
 → 결과 제출
 → 관리자 검토
```

회의에서는 다음 흐름을 사용합니다.

```text
녹음/오디오 업로드
 → STT
 → 회의록
 → AI 요약
 → TODO/결정 후보
 → 관리자 검토
```

화면 설계에서 중요하게 보는 기준:

- 일반 사용자와 관리자 메뉴를 역할에 맞게 분리
- 내부 상태값보다 사용자가 이해하기 쉬운 한글 상태와 행동 중심 표현 사용
- 검색 결과에서 근거 파일을 실제로 열어 확인할 수 있도록 연결
- 긴 목록은 페이지 단위로 나누고, 오래 걸리는 수집은 백그라운드 처리
- 로딩·빈 결과·오류·권한 없음 상태를 별도로 표현
- 데스크톱과 모바일에서 동일한 업무 의미가 유지되도록 반응형 레이아웃 구성
- 기능 수보다 **다음에 무엇을 해야 하는지가 보이는 화면**을 우선

### Python / AI Service — 수치 정제와 검증 중심

FastAPI 기반 AI 서비스는 LLM 호출만 담당하지 않습니다. 검색 품질과 입력 데이터 품질을 높이기 위한 전처리·정제 계층의 역할도 담당합니다.

주요 처리 영역:

- 문서 텍스트 정제
- 긴 문서 chunking
- multilingual embedding
- semantic search용 vector 생성
- OCR
- 회의 음성 STT
- AI 요약 및 구조화
- 중복되거나 불필요한 passage 제거
- 실패·재시도·timeout과 같은 AI 처리 상태 관리

특히 Python 영역에서는 단순히 모델 결과를 사용하는 것보다 **검색에 들어가는 데이터의 길이, 단위, 중복, OCR 신뢰도, 처리량과 실패 조건을 수치로 제어하는 것**을 중요하게 봅니다.

```text
원본 데이터
 → 형식 정리
 → 텍스트 추출/OCR
 → 불필요 데이터 제거
 → Chunk 분할
 → Embedding
 → 검색 후보 생성
 → 중복/품질 정제
 → RAG 입력
 → Evidence 검증
```

즉 Python 서비스의 목적은 AI를 많이 호출하는 것이 아니라, **LLM과 검색에 들어가기 전 데이터를 최대한 안정적으로 정리하고 검증 가능한 형태로 만드는 것**입니다.


## 핵심 구조

Hub는 단순 챗봇이 아니라 **회사 자료와 실제 업무 흐름을 연결하는 시스템**입니다.

```text
문서 / 회의 / GitHub / Google Drive / Slack / Notion
                    ↓
              통합 수집·색인
                    ↓
          검색 / AI 질문 / 근거 확인
                    ↓
          TODO / 결정 / 변경 / 일정
                    ↓
       일반 사용자 수행·제출
                    ↓
          관리자 검토·승인·반려
```

AI가 만든 결과는 바로 공식 업무가 되지 않습니다.  
**관리자가 원문과 근거를 확인한 뒤 담당자를 지정하고 확정**합니다.

## 사용자 역할

현재 역할 기준은 명확하게 분리되어 있습니다.

| 역할 | 주요 권한 |
|---|---|
| **일반 사용자 (MEMBER)** | 배정받은 업무 수행, 상태 변경, 도움 요청, 근거 확인, 완료 자료 제출, 일반 자료 전송 |
| **관리자 (ADMIN)** | AI 검토, 담당자 결정, 완료 승인·보류, 삭제·복원·영구삭제, 가입 승인, 사용자/조직/보안/검색 정책 관리 |

### 담당자 기준

- **할 일 담당자는 일반 사용자만 가능합니다.**
- 관리자는 담당자가 아니라 **결정권자/검토자**입니다.
- 일반 사용자는 다른 사람의 개인 업무 상태를 대신 변경할 수 없습니다.
- 완료 승인·보류·삭제는 백엔드에서도 관리자만 가능합니다.

### 관리자 교체

관리자는 프로젝트 생성자에 고정하지 않습니다.

- 관리자 역할은 **회사 관리 > 사용자 관리**에서 변경할 수 있습니다.
- 관리자가 교체되어도 관리자용 제출 자료는 특정 관리자 개인에게 묶이지 않습니다.
- 관리자 제출물은 **프로젝트 단위 관리자 제출함**에 남아 새 관리자가 이어서 확인할 수 있습니다.

## 할 일·일정 흐름

확정된 할 일은 다음 상태를 사용합니다.

- **시작 전**
- **진행 중**
- **보류**
- **도움 필요**
- **반려**
- **완료**

기본 흐름:

```text
AI 후보 생성
  → 관리자 검토
  → 담당자 지정·확정
  → 시작 전
  → 진행 중
  → 완료 제출
  → 관리자 검토
  ├─ 승인 → 완료
  └─ 반려 → 담당자 수정 후 재제출
```

담당자는 자기 할 일에서만 진행/보류/도움 요청/완료 제출을 할 수 있습니다.

### 완료 제출

완료 요청 시 다음 중 하나 이상의 근거가 필요합니다.

- 제출 파일 첨부
- `http://` 또는 `https://` URL 제출

파일과 URL이 모두 없으면 완료 제출할 수 없습니다.

완료 승인 대기 중에는 제출 근거가 바뀌지 않도록 서버에서 다음 동작을 잠급니다.

- 상태 변경
- 보류
- 도움 요청
- 제출 첨부파일 추가
- 제출 첨부파일 이름/메모 수정
- 제출 첨부파일 삭제

관리자는 제출 URL·첨부파일·업무 근거를 확인한 뒤 승인하거나 반려합니다.

## 할 일과 무관한 자료 제출

출장, 외근, 현장 확인, 참고 링크처럼 **등록된 할 일과 직접 연결되지 않는 자료**도 보낼 수 있습니다.

일반 사용자는 **자료 보내기**에서 관리자 제출함으로 다음 자료를 임의 제출할 수 있습니다.

- 파일
- URL
- 제목
- 설명/메모

관리자 제출함은 프로젝트에 귀속되므로 관리자 교체 후에도 기존 제출물을 이어서 볼 수 있습니다.

일반 사용자끼리 특정 상대에게 직접 보내는 파일 전송도 별도로 유지됩니다.

## 문서·검색·AI

Hub의 검색은 단순 키워드 검색만 사용하지 않습니다.

```text
질문
 → SearchQueryRouter
 → 파일명 / 메타데이터 / lexical / semantic 후보
 → RRF 기반 결합
 → deterministic rerank
 → 문맥 확장
 → RAG
 → Evidence 검증
 → 답변 + 근거 + 원문 열기
```

주요 원칙:

- 파일명이 명확하면 정확 일치를 강하게 우선합니다.
- 문서·회의·첨부파일은 Hub 자료로 함께 검색합니다.
- Evidence는 원문 snapshot과 content hash를 유지합니다.
- AI가 반환한 근거가 실제 검색 결과와 연결되지 않으면 근거 있는 답변으로 확정하지 않습니다.
- 문서 버전이 바뀌어도 기존 TODO의 근거가 자동으로 다른 버전으로 바뀌지 않습니다.

## 회의

회의는 다음 방식으로 입력할 수 있습니다.

- 브라우저 녹음
- 음성 파일 선택
- 음성 파일 드래그앤드롭

처리 흐름:

```text
음성
 → STT
 → 회의록
 → 요약
 → TODO / 결정 후보
 → 관리자 AI 검토함
```

실패한 분석 작업 기록은 별도로 삭제할 수 있습니다.

## 연결 서비스

지원 대상:

- **GitHub**
- **Google Drive**
- **Slack**
- **Notion**

연결 서비스에서 가져온 자료도 Hub 검색 인덱스에 포함됩니다.

백엔드는 대용량 가져오기를 한 번에 화면 요청에 묶지 않고 **백그라운드 작업과 페이지 단위 수집**을 지원합니다.

실제 계정별 토큰은 사용자 단위로 분리하는 것이 기본이며, 공유 토큰 fallback은 명시적으로 켠 경우에만 사용합니다.

## 기술 구성

```text
Browser
   ↓
React + TypeScript
   ↓
Spring Boot / Java 21
   ├─ 인증 / 권한 / 관리자 승인
   ├─ 프로젝트 / 문서 / 회의
   ├─ 검색 / RAG / Evidence
   ├─ TODO / 결정 / 변경 / 알림
   ├─ 관리자 기능
   └─ Connector
          ↓
FastAPI
   ├─ Gemini LLM
   ├─ Gemini STT
   ├─ multilingual E5
   └─ PaddleOCR
```

데이터 저장:

- 로컬 개발: **H2 file DB**
- 운영: **PostgreSQL + pgvector**
- 스키마 변경: **Flyway**
- 파일 저장소: 로컬/서버 storage 디렉터리

Flyway는 `common + 현재 DB profile` 조합에서 버전이 중복되면 애플리케이션이 시작되지 않으므로, 저장소 검수 스크립트가 중복 버전을 CI에서 검사합니다.

## 보안 기준

- JWT stateless 인증
- Access / Refresh Token 분리
- BCrypt 비밀번호 해시
- CSRF cookie token
- ADMIN / MEMBER 권한 분리
- 가입 승인
- 비활성/정지 계정 제어
- 프로젝트 접근 제어
- 실제 Secret은 Git에 저장하지 않음
- 회의 STT의 민감정보는 저장 전 비식별 처리 경로 사용

## 운영 배포

운영 배포는 Hub 저장소에서 직접 SSH 배포하지 않습니다.

```text
Hub main
  → Hub CI
  → chl4890620123-collab/Server
  → Central production deployment
  → 서버에서 Hub 소스 체크아웃
  → AI / Backend Docker 이미지 빌드
  → PostgreSQL + AI + Backend + Caddy 기동
  → 로컬 health 확인
  → 공개 배포 검증
```

즉 **Hub의 main push와 실제 운영 배포는 분리**되어 있습니다.

운영 배포 트리거와 서버 SSH/Compose 설정은  
`chl4890620123-collab/Server` 저장소가 중앙 관리합니다.

현재 운영용 public base URL 설정은 다음 주소를 기준으로 사용합니다.

```text
https://yellow.it.kr
```

운영 상태는 README에 고정 기록하지 않고 배포 워크플로의 실제 검증 결과를 기준으로 판단합니다.
